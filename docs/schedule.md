# 개발 전 테스트 계획

이 문서는 [agentic-rag-design.md](./agentic-rag-design.md) 8장(공통 RAG 및 에이전트 평가 체계 수립 계획)에서 계획만 세워 둔 검증 작업을, 실제 개발에 들어가기 전에 무엇을 어떤 순서로 할지 실행 관점에서 정리한 것임. 대화에서 오간 판단 근거를 요약하며, 아직 아무 코드도 실행하지 않은 상태에서 세운 계획이라 실제 착수 시 조정될 수 있음.

---

## 1. 테스트를 두 종류로 나눠서 접근함

같은 "평가"라는 말을 쓰지만 목적이 다른 두 활동을 구분해서 계획함.

### ① 달성도 확인 (Acceptance Test)

지금 고정된 설계(프롬프트, 모델, 질의 템플릿)가 골든셋 기준을 넘는지만 확인하는 것. 여러 옵션을 비교하는 게 아니라 "합격선을 넘는가"만 보므로 바꿔야 할 변수가 없음.

- RAG 여부와 무관하게 **10개 에이전트 전부**에 적용됨
- 설계가 다 끝난 뒤 한 번에 하는 게 아니라, **에이전트를 만들 때마다 그 에이전트만 즉시 돌려서 확인**함. 사실상 프롬프트 엔지니어링의 피드백 루프 자체가 이 과정임(만든다 → 골든셋으로 돌린다 → 8.2 루브릭으로 채점한다 → 기준 미달이면 프롬프트를 고치고 재실행한다)
- 전 에이전트가 다 붙은 뒤에는 통합 실행을 한 번 더 해서 8.3(Loop Efficiency 등 시스템 전체 지표)까지 확인하는 마지막 단계가 있음. 이건 ①을 반복한 뒤의 최종 확인이지, ①을 처음 수행하는 시점은 아님

### ② 비교실험 (Comparison Test)

"이 설계가 최선인가"를 검증하려고 실제로 변수를 바꿔 가며 비교하는 것. 아래 3절에서 정리하듯, 논의 결과 **RAG를 쓰는 3개 에이전트(tech_research, trl_eval, domain_eval)로 범위가 좁혀짐**. RAG를 안 쓰는 에이전트(market_eval, stakeholder_eval, evidence_check, synthesize, judge, report)의 설계 변수들은 비교실험 없이 근거만으로 확정하기로 했고, 그 판단 근거는 4절에 정리함.

## 2. 에이전트별 테스트 범위

| 에이전트 | RAG | ① 달성도 확인 | ② 비교실험 대상 |
|---|---|---|---|
| `select_tech` | X | 필요 없음(LLM 미사용, 설정값 로드뿐) | 없음 |
| `tech_research` | O | O (TechProfile 추출 품질) | **O** — 임베딩, 청킹, Query Rewriting |
| `trl_eval` | O | O (TRL 판단 품질) | **O** — 임베딩, 청킹, Query Rewriting |
| `domain_eval` | O | O (도메인 적용 판단 품질) | **O** — 임베딩, 청킹, Query Rewriting |
| `market_eval` | X | O (8.2 루브릭) | 없음(3절 참고) |
| `stakeholder_eval` | X | O (8.2 루브릭) | 없음(3절 참고) |
| `evidence_check` | X | O (규칙 단위 테스트) | 없음(3절 참고) |
| `synthesize` | X | O (8.2 루브릭) | 없음 |
| `judge` | X | O (판정 정확도 스팟체크) | 없음 |
| `report` | X | O (8.2 루브릭 + 인용 번호 안전장치 단위 테스트) | 없음 |

`select_tech`, `evidence_check`, `judge`는 LLM 생성물이 아니거나(규칙 기반) 이진 판정이라 8.2 LLM-as-Judge 루브릭 대신 **입력을 넣었을 때 의도한 출력이 나오는지 보는 단위 테스트**로 검증함. `report`의 인용 번호 안전장치(7.10에서 추가한, 다듬기 후 근거 번호 유효성 재검증 로직)도 같은 방식으로, 환각 번호가 섞인 입력을 일부러 넣어 원문 문장으로 되돌아가는지 확인하는 테스트가 필요함.

## 3. RAG 에이전트 비교실험 (3개 에이전트 대상)

### 3.1 임베딩 모델 비교

- **변수**: bge-m3, multilingual-e5-large, Qwen3-Embedding-0.6B (설계서 6.1절 후보)
- **지표**: Hit Rate@5, MRR (8.1절 정의)
- **방법**: 동일한 30개(~40개) 한국어 골든 질의셋에 세 모델을 각각 색인·검색시켜 비교
- **판단 기준**: bge-m3가 다른 후보보다 뚜렷이 낮으면 교체 (6.1절에 이미 명시된 기준)

### 3.2 청킹 전략 검증 (2단계 절 인식)

- **변수**: 절 구조 인식 없이 바로 800자 슬라이싱 vs 절 경계 안에서만 800자 분할(5장에서 채택한 방식)
- **지표**: `section` 메타데이터 정확도(청크가 실제로 속한 절과 라벨이 일치하는 비율), Hit Rate@K
- **방법**: 같은 Doc Pool을 두 방식으로 각각 색인해 비교. 특히 도메인 평가(7.4)의 "실험 환경 절 우선 재랭킹"이 절 라벨 정확도에 의존하므로, 이 재랭킹이 실제로 검색 품질을 끌어올리는지도 같이 확인
- **참고**: 이건 순수 설계 추론("절 경계를 먼저 잡아야 메타데이터가 정확하다")으로 도입한 장치라, 실제로 개선 폭이 있는지 아직 데이터로 본 적이 없음

### 3.3 Query Rewriting 효과 검증

- **변수**: Pre-retrieval Query Rewriting 적용 전/후 (이번에 7.2·7.3·7.4에 새로 추가한 장치)
- **지표**: Hit Rate@K, MRR
- **방법**: 같은 골든 질의셋을, 코드가 고정한 원본 질의 템플릿 그대로 검색했을 때와 GPT-5 mini로 리라이팅한 뒤 검색했을 때를 비교
- **판단 기준**: 개선 폭이 미미하면 리라이팅 호출 비용을 들일 이유가 약해지므로 제거를 재검토. 뚜렷하면 채택 근거가 데이터로 보강됨

## 4. 비교실험 없이 근거로만 확정한 결정 (재확인용 요약)

아래는 "왜 바꿔보지 않았는가"를 논의하며 정리한 결론임. 모두 설계 문서 본문에 근거가 반영돼 있고, 여기서는 판단만 요약함.

| 결정 | 비교실험을 안 한 이유 |
|---|---|
| 생성 LLM = GPT-5 mini | Structured Outputs 지원 여부 같은 하드 제약에서 연역적으로 도출됨. 6.3절에 GPT-5 mini vs Qwen3-8B 스키마 준수율·응답시간 비교가 이미 계획돼 있어 별도 실험 불필요 |
| 검색 앵커 키워드 추가 | 저비용·저위험 안전장치(질의에 단어 하나 추가). 이득이 명백해 A/B로 증명할 필요가 낮음 |
| web_search 파라미터(질의 개수 3개 등) | 정답이 있는 문제가 아니라 커버리지-비용 트레이드오프. 초기값으로 두고 구현 중 조정 |
| evidence_check 임계값(3건, 2배) | 통계적으로 도출한 값이 아니라 명시적 휴리스틱임을 문서에 밝히는 것으로 처리(7.7절에 한 줄 추가함) |
| Query Expansion | 이 프로젝트엔 불필요하다고 판단, 채택 안 함 |
| Query Transformation(HyDE) | 교차언어 검색에 이론적으로는 맞지만 LLM 호출 비용과 tech_research의 안정성 원칙(재검색 없음)과 충돌 여지가 있어 채택 안 함 |
| Hybrid Retriever(Dense+Sparse) | 코퍼스가 작고(300~400청크) 핵심 난제가 교차언어라 Sparse의 이점이 제한적. 다만 bge-m3가 Sparse 출력도 낼 수 있어 **Dense 단독이 목표 지표(Hit Rate@5 ≥ 0.8)에 못 미치면 1차 확장 후보로 이미 문서에 남겨둠**(6.1절) |
| Multi-hop Retriever | 이 도메인의 질의는 전부 단일 홉으로 답이 나와 도입 근거 없음 |

## 5. 사전 준비물 체크리스트

실제 테스트를 시작하려면 아래가 먼저 갖춰져야 함.

- [ ] **실행 가능한 코드**: LangGraph 그래프, 10개 에이전트 노드, `paper_search`/`web_search`/`summarize_sources` 도구
- [ ] **Doc Pool 실제 색인**: PDF 6편 확보 → PyMuPDF 파싱 → 정규식 절 인식 → 청킹 → bge-m3 임베딩 → FAISS 색인
- [ ] **Golden Dataset**: 한국어 질의 30~40개(Retrieval용) + 관점별 Fact-Check 체크리스트(8.4절 기준 40~48개) + 보고서 체크리스트 9개 — 조원이 논문을 읽고 직접 라벨링해야 함(자동화 불가, 가장 오래 걸림)
- [ ] **비교 대상 임베딩 모델**: multilingual-e5-large, Qwen3-Embedding-0.6B 실제 로드
- [ ] **API/실행 환경**: OpenAI API 키(GPT-5 mini), Ollama(Qwen3-8B), Tavily API 키
- [ ] **실행 로그 계측**: 도구 호출(도구명, 질의, 필터, 재시도 여부)을 구조화 로그로 남기는 코드 — Tool Calling Accuracy·Loop Efficiency 측정에 필요, 현재 설계엔 없어 추가해야 함
- [ ] **LLM-as-Judge 채점 스크립트**: 8.2 루브릭(정확성·완전성·중립성·근거연결성)을 실행할 프롬프트와 채점 로직
- [ ] **골든 레퍼런스 요약**: 8.2 "비교 기준선"에 쓸, 조원이 직접 작성한 기준 요약본

## 6. 진행 순서(제안)

1. Doc Pool 색인 구축 + Golden Dataset 제작 (3장 임베딩/청킹 비교실험의 전제 조건)
2. RAG 에이전트 3개 구현 → 3.1~3.3 비교실험 → 여기서 확정된 임베딩·청킹·리라이팅 설정으로 고정
3. RAG 에이전트 3개에 대해 ① 달성도 확인 (8.2 루브릭)
4. 비RAG 에이전트 7개 순차 구현 → 각각 ① 달성도 확인
5. 전 에이전트 통합 실행 → 8.3 Agent System 지표(Tool Calling Accuracy, Loop Efficiency) 확인
6. 문제 발견 시 해당 에이전트로 돌아가 프롬프트/설계 조정 후 재실행
